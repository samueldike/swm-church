# AGENTS.md — SWM FastAPI

## Stack
FastAPI + async SQLAlchemy + Postgres (asyncpg) + Jinja2 + Celery/Redis. Python 3.12. No `pyproject.toml` — deps in `requirements.txt`.

## Commands
| Purpose | Command | Expected |
| Typecheck | `py -m py_compile app/routes/admin.py && py -m py_compile app/main.py` | exit 0 |
| Tests | `pytest tests -q` | all pass (root-level `test_login_http.py` needs a live server on :8000) |
| Lint | `ruff check .` (if installed) else `py -m py_compile` | exit 0 |
| Dev server | `uvicorn app.main:app --reload --port 8000` | http://localhost:8000 |

## Conventions
- Routes: `app/routes/admin.py` is god file (~6000 lines). Split by `# ─── Section ───` comments. Keep new admin routes there, use `_get_admin` + `_redirect`. Access: see "HQ + branches model" (no bare `role == "super_admin"` checks for module access — use `has_perm`).
- Templates: `app/views/admin/*.html` — Jinja, `url_for('admin.xxx')` with dots (e.g., `admin.dashboard.metrics`). Check `app/routes/admin.py` name.
- CSRF: all POST forms include `csrf_token`; the `csrf_protect` router dependency (`app/core/csrf.py`, wired in `app/main.py`) validates it against `session["csrf_token"]` (JSON fetches send `X-CSRF-Token`).
- Flash: `_redirect` sets both `flash_messages` and `session[flash_type]`; `app/core/template.py` pops after render — message shows once.
- Auth: `app/core/auth.py` reads `admin_session_timeout_minutes` from settings_cache, not hardcoded 1800.
- Uploads: whitelist `.jpg/.jpeg/.png/.webp/.gif` for images, audio `mp3/wav/m4a/...` max `TELEGRAM_MAX_UPLOAD_MB` (2000MB) images 5MB; use `slugify` + suffix for branch/department/story slugs.

## Production server (swm.tutapis.com)
- `/opt/swm` runs **`docker-compose.prod.yml`** (its `.env` sets `COMPOSE_FILE=docker-compose.prod.yml`): bind-mounted folders (`app/media`, `telegram-archive`, `documents`), app on `127.0.0.1:8085` behind the host's nginx. `docker-compose.yml` is the self-contained variant for a fresh server. Change the prod file in git, never by hand on the server.
- Deploy: `git pull --ff-only && docker compose build app && docker compose up -d --no-deps app`. The WhatsApp gateway has its own file (`-f whatsapp-gateway/docker-compose.yml`).

## Gotchas
- Postgres columns are `TIMESTAMP WITHOUT TIME ZONE` (naive). Always compare with naive `datetime.utcnow()`, not `timezone.utc` aware, else asyncpg `can't subtract offset-naive` error (see metrics).
- Sermon `status` is lowercase `published/draft`; form sends capitalized `Published` — lower it.
- `Branch.slug` / `Department.slug` must be unique — use loop with `select(...).where(slug==...)`.
- `ContactInquiry.branch` and `Sermon.branch` need `selectinload` else `MissingGreenlet` on `inquiry.branch.name`.
- `migrate_mysql.py` regex for `INSERT ... VALUES (...);` breaks on `;` inside `'...&amp;...'` — use scan for `;` outside quotes.

## Telegram audio distribution
- **Audio is never re-encoded.** Telegram gets the file exactly as uploaded. Cloud Bot API caps `sendAudio` at 50MB; **large files** (the self-hosted `telegram-bot-api`, `--local`) raise it to 2000MB. A file over the limit in use fails with an actionable reason; there is no compression fallback.
- Large files are switched on by the HQ Administrator in **Settings → Audio distribution** (`telegram_large_files` = `on`), after saving the church account's **App api_id / App api_hash** (my.telegram.org; account-level, not the bot token). Both are in `ENCRYPTED_SETTING_KEYS`; never put them in `.env` or compose. "Turn on" proves the local server logs the bot in (`telegram_local.server_check`) before flipping the switch; a failure leaves it off.
- The container cannot read the DB, so `telegram_local.sync_credentials()` writes them to `TELEGRAM_BOT_API_CONF_DIR` (`/run/swm-telegram`, volume `telegram_bot_api_conf`, rw in `app`, ro in the container) on save and at app startup; `deploy/telegram-bot-api/entrypoint.sh` waits for them and restarts the server when `stamp` changes. The container idles until keys are saved.
- The app never reads bot updates, so Telegram's `logOut` step is skipped: the same bot works on both servers and switching is instant/reversible. `TelegramDistributor.is_local` is set from Settings by `_get_credentials()`; use `await upload_limit()`. `resolve_file` always uses the cloud API (a `--local` server answers with paths on its own disk).
- In local mode files are handed over as `file://` paths, never streamed — so `media_files` must mount at the **same absolute path** in `app`, `worker` and `telegram-bot-api`. That path is `MEDIA_ROOT` (`/app/media`, baked into the Dockerfile).
- Distribution failures: network/429/5xx retry automatically (`_DISTRIBUTE_BACKOFF`, ~2.5h, honouring `retry_after`); permanent rejections record Telegram's own `description`; the Messages page shows it with a "Send to Telegram again" action (`admin_messages_redistribute`).
- All media paths resolve via `app/core/media.py:to_abspath()`. Never rebuild them from `__file__` — `MEDIA_ROOT` may differ from the package dir.
- Distribution is async: the create route queues `distribute_audio_task`, which sends to Telegram, writes `telegram_file_id`, records `Sermon.distribution_status["telegram"]`, then chains `transcribe_audio_task`. The HTTP request returns immediately.
- Transcription prefers the **local file** and only falls back to Telegram, so it is no longer bound by the 20MB `getFile` ceiling.
- **Telegram archive** (`/admin/telegram-archive`, HQ Administrator only, `app/core/telegram_archive.py`): bots cannot read channel history, so it signs in as a Telegram *user* (Telethon/MTProto, same App api_id/api_hash). The StringSession is encrypted in `telegram_user_session`; "Sign out" calls `log_out()` and deletes it. Jobs `scan → download → import` run in `telegram_archive_task` (progress in the `telegram_archive_job` setting, heartbeat-based `job_running`), rows in `telegram_archive_items` (unique per channel+message, so re-runs never duplicate).
- Archive files live in `TELEGRAM_ARCHIVE_DIR` (`/app/telegram-archive`, mounted in app **and** worker), deliberately **outside `MEDIA_ROOT`**, which nginx and the app serve publicly. Sermons made from them store `audio_file_path = "archive/<path>"`; `to_abspath` resolves that prefix inside the archive dir only. They play through `messages_stream` once published; they are drafts until an admin publishes them.
- `Sermon.original_file_size` is a Postgres `INTEGER` — max ~2.1GB. Raising `TELEGRAM_MAX_UPLOAD_MB` past 2048 requires a `BIGINT` migration first.

## Secrets & API keys
- All API keys are managed in Admin → Settings, never in code. Keys in `ENCRYPTED_SETTING_KEYS` (`app/core/settings_cache.py`: Anthropic/OpenRouter/Groq/Gemini keys, Telegram bot token, Paystack/Flutterwave secrets, Flutterwave encryption key, Resend) are Fernet-encrypted in `site_settings` (`enc:v1:` prefix), keyed from `SECRET_KEY`. To add a secret: add it to that set and render it with the `secret_field` macro.
- Secrets are **write-only in the UI**: `admin_settings` strips them from the template context and passes only `secret_status` (state + last 4). On save a blank box keeps the value, typing replaces it, `clear_<key>=1` removes it. Never echo a secret into HTML.
- Changing `SECRET_KEY` makes stored secrets unreadable (the page shows "Saved but unreadable"); set a real `SECRET_KEY` before saving keys. Plaintext rows from before encryption are encrypted at startup (`encrypt_plaintext_secrets`).
- `.env` `PAYSTACK_*`/`FLUTTERWAVE_*`/`ANTHROPIC_*` remain only as fallbacks when nothing is saved in Settings.

## Books Pub (AI devotionals & books)
- Sidebar **Publishing → Books Pub → Daily Devotional / Book** (`media` permission: HQ media and HQ Administrator). Routes `/admin/publications/{devotionals|books}/...` live in the `# ─── Books Pub` section of `app/routes/admin.py`; every handler starts with `_pub_guard`.
- Models `app/models/publication.py`: `Publication` → `PublicationSource` (one message = a devotional "main topic" / a book chapter) → `PublicationSubtopic` (a day / a section). Tables are created by `create_all`; no migration script.
- Pipeline: transcripts (existing message, audio upload → `transcribe_audio_task`, or pasted/.txt/.docx transcript, all stored as **draft** `Sermon`s) → **Generate Topics** → **Generate Contents** → **Generate/Update Devotional** → Word-like editor (`pub-editor.html`) → `.docx`/`.pdf` export.
- AI: `app/core/ai.py` is a multi-provider client over httpx: **Anthropic, OpenRouter, Groq, Google Gemini** (`PROVIDERS` dict). Admin → Settings → AI drafting holds one key + model per provider and the **default provider** (`ai_default_provider`); all are read from the DB on every call, so the app and Celery worker follow changes with no restart. `.env` `ANTHROPIC_*` is only a fallback. To add a provider: add it to `PROVIDERS` + `build_request`/an extractor in `ai.py` and its `*_api_key` to `ENCRYPTED_SETTING_KEYS`; the settings UI renders from `PROVIDERS`. Models: `SUGGESTED_MODELS` (hand-curated, will age) is what Settings offers until an admin clicks **Refresh model list**, which calls the provider's list-models endpoint with the saved key and caches the live list in `site_settings` (`ai_models_<provider>`); the field is a free-text combobox, so any model id can be typed (validated by `valid_model_id`, and URL-quoted for Gemini). Update `SUGGESTED_MODELS` when providers retire models. There is no per-project provider; a default with no key means drafting is off (no silent fallback to another provider).
- Jobs run in Celery (`generate_topics_task`, `generate_contents_task`); if the broker is unreachable `enqueue_*` falls back to an in-process asyncio task. From a request handler always queue with `await app.core.jobs.enqueue(task, *args)`, never `task.delay()`: `.delay()` is blocking and retries a dead broker for minutes, freezing the whole event loop. Rows are claimed `queued → processing` atomically. Stuck jobs: "Cancel jobs" (`reset-jobs`). The workspace polls `/status` and swaps `#pub-live`, so reorder/drag listeners are delegated on that element.
- The editor document is sanitised HTML (`app/core/publication_html.py:sanitize`, a whitelist — never store raw editor HTML). Sections are wrapped in `<div data-block="cover|day:ID|chapter:ID|section:ID">`. **Update** re-assembles from the topics but keeps blocks that already exist in the document (user edits survive) and only renumbers `Day N`/`Chapter N`; **Rebuild** discards edits. Don't remove `data-block` wrappers when changing the generators.
- Export: `app/core/publication_export.py` (python-docx, reportlab). PDF uses standard fonts (WinAnsi): characters outside cp1252 are folded/`?`. The editor's "Print / Save as PDF…" gives full-Unicode PDFs via the browser.
- Tests: `tests/test_publications.py` (pure logic, no AI/network). The word-count target (~200/day) is enforced only by one shorten-retry when a draft exceeds 300 words.
- **Print templates** (devotionals only): editor → Export → *Designed PDF (template)…*. Registry `app/core/devotional_templates.py:TEMPLATES` (first: **SWM Lite**, `app/views/print/devotional-swm-lite.html`, a greyscale print-book page per day: mirrored left/right pages via `@page :left/:right` margin boxes, page number `counter(page)` started by `@page:first{counter-reset}`, logo in greyscale, date badge from `start_date + day-1`, Bible-in-one/two-years strip computed Genesis→Revelation). Content is parsed from the editor document (edits win), falling back to the subtopic fields. **WeasyPrint** renders (pango libs in the Dockerfile; fonts in `app/static/fonts/print/`, OFL). Each day gets the largest of 4 type sizes that fits one page (`_fit_many`: batch render, re-render only overflowing days), long books split over spawn processes and merged with pypdfium2: a year ≈ 70 s. The export is an in-process job (`_PUB_EXPORTS`, POST → poll → `/file`, owner only, 1 h); thumbnails are page 1 of the real PDF (pypdfium2). To add a template: a new HTML in `app/views/print/` + an entry in `TEMPLATES`; keep `id="day-N"` anchors and `fit-0..3` classes. Tests: `tests/test_devotional_templates.py`.

## Video Clipper (/admin/clipper)
- Long video (link via yt-dlp, or upload streamed raw to `/clipper/{id}/upload`) → ready-to-post shorts. Code `app/core/clipper/` (read its `__init__.py`), models `app/models/clipper.py`, routes `# ─── Video Clipper` at the end of `admin.py`, UI `admin/clipper*.html` + `static/js/clipper.js` + `static/css/clipper.css`.
- **Access** `options.allowed`: HQ Administrator, branch admins, HQ Media, and the HOD of a department whose name contains the word "Media"; permission `clipper` is checked per person in `policy.py` (like WhatsApp). Projects belong to a church (`church_of`); only the HQ Administrator sees every church's.
- **Pipeline** (Celery, `acks_late=False`, a restart shows "Stopped" + Retry, which resumes from the files already made): `clip_fetch_task` (queue `clipper`) → `clip_transcribe_task` (queue **`transcription`**, shares the transcriber's Whisper model; word timestamps) → `clip_compose_task` → `clip_render_task` (`clipper`). The `clipper` worker is its own compose service (`-c 1`, `cpus: 3`). From a request always `await app.core.jobs.enqueue`.
- **Editorial** (`editorial.py`, ported from VidViralPicker): structure pass (where the message is), compose (every sentence with its *playing* seconds), deterministic `fit_short` (whole sentences only, no id in two shorts), review (keep/revise/reject). `style=passage` (default) keeps each short one stretch of the video (≤3 skipped sentences); `assembled` may join distant parts. Uses the default AI provider (`ai.complete`).
- **Cut** (`cut.py`, pure): segments snap to word boundaries with breath padding; pauses ≥ `speech.PAUSE` (word gaps **or** the measured silence map) and fillers are removed; connectives only at the very start. **Camera** (`reframe.py`): YuNet faces at 6 fps, a dead-zone + speed-limited virtual camera, hard cut on source cuts, rendered as a piecewise-linear ffmpeg `crop` x-expression. **Captions** (`captions.py`): ASS word-by-word (Poppins in `clipper/assets`), plus `.srt`. Render: per-segment encodes (12 ms audio fades), concat, one final pass (subtitles + `loudnorm` −14 LUFS).
- **Files** in `settings.clipper_dir` (`/app/clipper`, prod bind `./clipper`, mounted in app, transcriber and clipper), never under MEDIA_ROOT, never in git/image (anchored `/clipper/` ignores: `app/core/clipper` is code). Served only by `admin_clipper_file`. Sources are deleted `CLIPPER_KEEP_SOURCE_DAYS` (14) after a project finishes (scheduler housekeeping); shorts stay. New work refuses below 6 GB free disk.
- **yt-dlp goes stale** (sites change): bump the pin in requirements + constraints when links start failing. YouTube refuses this server's IP ("Sign in to confirm you're not a bot"): the HQ Administrator uploads a signed-in browser's cookies.txt under Video Clipper → **YouTube access** (`clipper_youtube_cookies`, in `ENCRYPTED_SETTING_KEYS`, written to a 0600 temp file per download and deleted); without it, upload the file. Links are fetched whole at full speed and cut locally (`trim_upload`): yt-dlp `--download-sections` runs at real time.
- **Silence map** is adaptive (`media.silences_from_levels`: threshold between the recording's own noise floor and speech level); ffmpeg `silencedetect` at a fixed dB found nothing in a real service. Word timings are corrected against it (`cut.true_words`) before cutting.
- Passage shorts get back what a sentence leans on (`editorial.repair_references`: a skipped line before "He says…", the line before an opening "And so he…"), and the reviewer sees left-out lines inline.
- Tests: `tests/test_clipper.py` (pure: access, fitting, cut, camera, captions, silences, cookies).

## HQ + branches model (read before touching access, audio, giving)
- **One HQ, many branches.** `Branch.is_hq` marks HQ (`ensure_schema()` flags exactly one at startup; `get_hq_branch_id()` never invents a second). Everything owned by a branch (`branch_id`) stays inside that branch.
- **Roles** (`app/core/access.py`): `super_admin` (HQ Administrator), `hq_media`, `hq_finance`, `hq_pastoral`, `branch_admin`, `resident_pastor`, `hod`. Legacy strings `admin`/`branch_super_admin` mean `branch_admin` (`normalize_role`; rewritten at startup). HQ staff roles are scoped to HQ's own records + their module; only `super_admin` crosses branches.
- **Two layers of access control — keep both.** (1) `app/core/policy.py:admin_policy` is a router dependency mapping every `/admin/*` URL to a permission (`access.required_permission`); add new admin URLs to `_RULES` in `access.py`, and the sidebar uses `can('perm')`. (2) Object level: `_foreign(admin, record.branch_id)` in `admin.py` on every update/delete/show of a branch-owned record; never trust a posted `branch_id` for non-HQ admins. `scripts/hq_branch_checks.py` (also run by `tests/test_hq_branch.py`) and `scripts/rbac_matrix.py` must stay green.
- **Audio:** the public website, home page, podcast feed, stream and download show **HQ-owned messages only** (`_hq_only()` in `public.py`). A branch's messages never reach the HQ site.
- **Telegram is per branch.** HQ uses the site-wide Settings; a branch uses only what it saved in `branch_settings` (encrypted bot token + channel id, `app/core/branch_settings.py`). `TelegramDistributor(branch_id)` **never falls back to HQ's bot**; the upload form only pre-ticks Telegram when the owner has credentials. Tasks pass `sermon.branch_id`.
- **Giving has two switchable models** (`giving_model` in Settings: `central` | `branch`). `Giving.branch_id` = who the gift is for; `gateway_owner` = whose payment account took it (`hq` | `branch`, branch keys in `branch_settings`, encrypted); gifts can also be recorded by hand (`method` cash/transfer/...). Remittances (`/admin/remittances`, `app/core/finance.py:branch_position`) show who owes whom from each branch's `hq_share_percent`.
- Public contact/prayer forms take a branch (`_pick_branch_id`, falls back to HQ). Prayer requests are pastoral: branch admins see only their branch's.
- Money is need-to-know: only `donations`/`remittances` permission holders see it; branch admins see only their branch; the dashboard giving trend is scoped the same way.
- **Ministers & Resident Pastor.** `Minister` (`app/models/minister.py`) is bio-data for HQ's and each branch's ministers (`/admin/ministers`; branch admin / HQ pastoral: own church, HQ Administrator: all). A minister can be made a HOD (branch admin or HQ Administrator) or Resident Pastor (**HQ Administrator only**, one per church, HQ counts as a church): creates/converts a console login with a one-time temporary password (no email is sent). `resident_pastor` is not selectable in the manual admin form.
- **Resident Pastor review gate** (`_unit_report_scope_filter`, `_rp_pending_condition` in `admin.py`): if a church has an active Resident Pastor, a department report submitted after `resident_pastor_since` (branch setting) is invisible to that church's office (branch admin / HQ Administrator for HQ's own church) until the Resident Pastor appends a comment (`status` -> `reviewed`); then the office adds `senior_pastor_comment` and cannot rewrite the RP's. Older reports and churches without an RP are unaffected; drafts are never visible to reviewers. Removing the RP releases held reports.
- **Ministers & Resident Pastor.** `Minister` (`app/models/minister.py`) = bio-data for HQ's and each branch's ministers (`/admin/ministers`; branch admin / HQ pastoral: own church, HQ Administrator: all). A minister can be made a HOD (branch admin or HQ Administrator; a HOD who is not a minister is invited from the HODs page) or Resident Pastor (**HQ Administrator only**, one per church, HQ counts as one). Both create/convert a login with a one-time temporary password (no email). `resident_pastor` is not selectable on the manual admin form.
- **Resident Pastor review gate** (`_unit_report_scope_filter`, `_rp_pending_condition`): with an active Resident Pastor, a department report submitted after `resident_pastor_since` is invisible to that church's office (branch admin; HQ Administrator for HQ's own church) until the RP appends a comment (status -> `reviewed`); the office then adds its own comment and cannot rewrite the RP's. Drafts are never visible to reviewers; churches without an RP are unchanged.
- **Account control.** `Admin.session_version` is bumped on password reset/change, deactivation and role/branch moves; `get_current_admin` refuses a session whose version differs, an inactive account, or a user of a closed branch. `must_change_password` (temporary/reset passwords, minister appointments, well-known defaults like `admin123` flagged at start-up by `flag_default_passwords`) sends the user to `/admin/profile` until they choose their own (`PasswordChangeRequired` in `policy.py`). `hods/{id}/update|edit` only act on `role == "hod"` accounts.
- **HQ -> branches.** `/admin/announcements` (HQ Administrator writes; branch admins, Resident Pastors and HQ staff read; shown on the dashboard). HQ's published events show read-only on branch calendars (`_visible_event_scope`). Branch admins get `/admin/activity` (their own branch's audit trail). Dashboard attendance comes from submitted Branch Reports only and is scoped to the viewer's branch.
- `tests/test_hq_branch.py::test_every_admin_route_is_covered_by_the_access_policy` fails if a new `/admin` route has no rule in `access._RULES`.
- New columns on existing tables must be added to `_ADDED_COLUMNS` in `app/database.py` (create_all does not alter tables).

## Blog (admin; public pages are still /stories)
- Admin "Stories" became **Blog**, modelled on WordPress Posts: `/admin/blog` (All Posts: status links with counts, search, bulk actions, month/category filters, hover row actions, Quick Edit, Trash with Undo), `/admin/blog/new` + `/{id}/edit` (block-editor-style screen: Save draft / Preview / Publish with a pre-publish check, sidebar with visibility, date, slug, author, sticky, categories, tags, featured image, excerpt; local backup + unsaved-changes warning), `/admin/blog/categories|tags`. `/admin/stories` 301-redirects. Routes are the `# ─── Blog` section at the end of `admin.py`; rules in `app/core/blog.py`; permission `media`.
- The model is still `Story` (`stories` table). Statuses: `draft`, `pending`, `published`, `future` (Scheduled), `private`, `trash`. Only `published` is public. A `future` post goes live via `blog.publish_due()` (scheduler); Trash keeps the old status in `trashed_status` so Restore puts it back; permanent delete only from the Trash.
- `Story.published_at` is **timestamptz** on Postgres: always write aware UTC (`blog.now_utc()`, `blog.aware()`); the editor's date is church time (`platform_timezone`) converted with `geo.to_utc`.
- Categories are the Settings → Lists `story_categories` list (the editor's "Add New Category" and the Categories screen write to it); a post stores `categories`/`tags` as JSON name lists and `category` = the first category (public cards). Content goes through `blog.sanitize` (publication whitelist + `img`/`pre`/`code`/`figure`).

## Documents (office library, /admin/documents)
- Every console user (all roles, HODs too: permission `documents`). Models `app/models/document.py`; rules `app/core/documents.py`; routes are the `# ─── Documents` section at the end of `admin.py`; UI `admin/documents.html` + `static/js/documents.js` + `static/css/documents.css`.
- Files live in `settings.documents_dir` (`/app/documents`; production: the `/opt/swm/documents` folder, `docker-compose.prod.yml`), **never under MEDIA_ROOT** and never in the image (`.dockerignore`), and are served only by `admin_documents_file` after `access_of()`. Allowed types: `documents.TYPES` (no programs, scripts, HTML or SVG); only `INLINE` types open in the browser (text sandboxed); max `DOCUMENTS_MAX_UPLOAD_MB` (100).
- Who sees a file: owner; `visibility` `church` (same church, `church_of`) / `everyone`; explicit `DocumentShare` to `user:<id>`, `role:<hq role>`, `office:<branch id>` (branch admin + Resident Pastor; HQ: HQ Administrator), `hods:<branch id>`; the HQ Administrator sees everything except `private`. `edit` lets someone rename, add notes/tags, move and upload versions; only the owner (or HQ Administrator) shares, changes visibility, trashes and deletes. Use `visible_condition()` for lists and `access_of()` for one file: never write a new check.
- "Send" = view share + `DocumentDelivery` (Received box, note, per-person `DocumentRead`, sidebar badge `documents_unread`); an email notice goes only when `mailer.can_send()`. Activity is the audit log (`target_type="document"`). Tests: `tests/test_documents.py`.

Campaigns: `/admin/campaigns` (HQ media / Administrator).

Checks: `scripts/site_checks.py` (also run by `tests/test_public_site.py`).

## WhatsApp (each church links its own account)
- Gateway: `whatsapp-gateway/` (Node 20, `@wppconnect-team/wppconnect` 2.3.6 driving WhatsApp Web in headless Chromium), its own compose project on the main network: `cd /opt/swm && docker compose -f whatsapp-gateway/docker-compose.yml up -d --build`. Container `swm-whatsapp`, internal only (`http://whatsapp:4100`), every call needs `Authorization: Bearer $WA_GATEWAY_TOKEN` (in `/opt/swm/.env`, read by the app and the gateway; the app also reads `WA_GATEWAY_URL`). Logins live in the Docker volume `swm_whatsapp_data`: **never delete it**, or every church must scan again.
- One session per church: tenant id `b<branch id>` (`app/core/whatsapp.py:tenant`). The gateway keeps `registry.json` (status, number, QR while pairing) and restores every "connected" session at boot; a watchdog (60s) relaunches silent ones, a reaper kills orphaned Chromiums, stale Chromium locks are cleared before launch, `autoClose` stays 0. Only **Disconnect** (or removing the device on the phone) logs out and wipes the login. These rules were ported from unana-ai's service; see the header of `whatsapp-gateway/src/sessions.js` before changing any of them.
- Chats and messages are read live from WhatsApp (nothing stored); scheduled posts and statuses are `WhatsAppPost` rows (`app/models/whatsapp.py`) sent by `app/core/scheduler.py` -> `whatsapp.process_due` (claimed atomically; a disconnected account makes a due post wait up to 6 hours, then fail). Attachments are saved under `MEDIA_ROOT/whatsapp/b<id>/` and handed to the gateway as paths (it mounts `app/media` read-only and refuses paths outside it).
- Access (`app/core/whatsapp.py:allowed`, enforced in `policy.py` for `/admin/whatsapp*`): HQ Administrator for every church (church picker); the HOD of a department whose name contains the word "Media" by default; any HOD or Resident Pastor when granted (`Admin.whatsapp_access` = `grant` / `deny` / empty). Grants: HQ Administrator for anyone, a branch admin for their own branch (`POST /admin/access/whatsapp/<id>`, buttons on the HOD and administrator edit pages).
- **Anti-ban guardrails (do not weaken without a reason).** Two layers:
  (1) `whatsapp-gateway/src/guard.js`, on EVERY send (chat, Post to many, forward, poll/location/contact, status, group create/add): rolling per-account limits per minute/hour/day (`LIMITS`; `cold` = first message to a number that is not a saved contact, `new` = first message to a saved contact), saved in `/data/guard.json`; a brake (`failure()`) pauses bulk sending and first messages for 6 h when WhatsApp pushes back (rate-overlimit/spam/restricted…) or 1 h after 5 failures in a row (replies to existing chats still work); `typeLikeAPerson` before each bulk message. Refusals are HTTP 429 with `retryAt`. Endpoints: `GET /sessions/:id/guard`, `POST .../guard/resume` (app: HQ Administrator or branch admin only), `POST .../check-targets`.
  (2) Post to many (`app/core/whatsapp.py`): never sent inside the request; `process_due` drips `PER_TICK` recipients per scheduler round with `GAP_SECONDS` pauses, resumes from `result` (nobody twice), `locked_until` stops double sending, waits on 429 until `retryAt`, sends at any hour the sender chooses (no night hold); at most `MAX_TARGETS` chats / `MAX_PEOPLE` people per post; the create route refuses "cold" numbers; `{name}` personalises each message; Stop works while sending. Tests: `tests/test_whatsapp.py`, `whatsapp-gateway/test/guard.test.mjs`.
- Status posting goes through WA-JS (`window.WPP.status`) so success is only reported when WhatsApp answers (`src/status.js`). WhatsApp Web automation is unofficial: keep posting volumes human, or WhatsApp may restrict the number.

## Reliability rules learned from the promise audit (`PROMISE_AUDIT.md`)
- **Test on Postgres, not just SQLite.** SQLite hid: stale id sequences, `VARCHAR(n)` overflows, unique-index violations, timestamptz columns. Clone the real DB (`CREATE DATABASE swm_audit TEMPLATE swm_db` with the app stopped) and run flows against the clone.
- `app/database.py:sync_sequences()` runs at startup and repoints every Postgres id sequence at `MAX(id)`. Anything that inserts rows with explicit ids (migrations/imports) relies on it.
- Many-to-one relationships used by templates are `lazy="selectin"`, so `x.branch.name` in a template cannot raise `MissingGreenlet`. Keep that when adding relationships.
- Unique columns: check first with `_value_taken()` (admin.py) and show a message; `main.py` has an `IntegrityError` handler as a safety net, not a substitute. Clamp public input to the column length.
- Every public form/API auth path is throttled (`app/core/throttle.py`, per process). Admin login: 5 failures/email, 10/IP per 15 min.
- Visitor-facing notices go through `partials/public-flash.html` (included by `site-page-close.html` and `home.html`). Do not read `session[...]` keys directly in page templates.
- Anything collected from visitors needs an admin page: Prayer Requests, Subscribers, Donations exist; CSV exports use `_csv_response` (neutralises `= + - @`).
- Giving: canonical paid status is `completed`; callback verifies amount (`mismatch`) and treats provider "pending" as pending.
- **Gateways** are `payment.GATEWAYS` (Paystack, Flutterwave, Bachs); the admin picks one in Settings → Giving gateway (`active_giving_gateway`; a branch's own in Branch settings). **Bachs**: hosted checkout sessions, major-unit decimal amounts, NGN minimum ₦1,000 (`BACHS_MINIMUMS`), host chosen by key prefix (`sk_sandbox_`/`sk_live_`); verification needs its `checkout_id`, stored in `Giving.gateway_txn_id`; `verify_bachs` refuses a session whose reference is not the gift's. Webhook signing secret is a separate setting (`bachs_webhook_secret`, HMAC-SHA256 of `timestamp.body`, 300 s tolerance).
- **Confirming online gifts goes through `app/core/giving_reconcile.py:reconcile()` only** — the callback, the webhooks (`/give/webhook/paystack|flutterwave|bachs` on `open_router`; set them in each gateway dashboard), the scheduler's re-check of pending gifts (10 min–7 days old, every 30 min; unpaid after 72 h → `abandoned`) and Donations → "Re-check". A gateway that can't be reached (`error`) never changes the gift; `completed` is claimed with a conditional UPDATE so only one receipt is sent. Audio routes use `_content_disposition` (header-safe) and `_serve_local_audio` (HTTP Range).
- Regression tests: `tests/test_audit_regressions.py`.

## Global churches (countries, money, time, lists)
- **Places are ISO codes, never free text** (`app/core/geo.py`): `country_code` (ISO 3166-1, `NG`), `region_code` (ISO 3166-2, `NG-EB`; the UK uses the level below its four nations), city tidied and reusing the spelling already recorded in that region (`_canonical_city`). The text columns (`country`, `state`, `state_of_origin`) are display names kept in sync. Every form uses the `location_fields` macro; `/geo/<CC>.json` feeds its region list.
- **One platform currency: HQ's** (`app/core/platform.py:platform_currency`, set on HQ's branch page). All giving, totals, remittances and website amounts use it, whoever's gateway takes the payment; branches have no currency (`Branch.currency` is NULL except HQ). Each gift still stores `currency`, so if HQ ever changes it, older gifts are reported separately (dashboard/donations/remittances group by currency, never sum across). Gateways are always told the currency; amounts go in the currency's minor unit (`geo.minor_units`); verification checks currency AND amount.
- **Time is per church**: `Branch.timezone` (IANA). Event times are naive wall-clock in their church's zone; `.ics` and Google links are UTC (`ics.event_tz`, `geo.to_utc`, DST-aware); reminders are stored in UTC. HQ's zone (`platform_timezone`) is the default for HQ-wide items.
- **Phones** are stored E.164 (`geo.normalize_phone` with the church's country; HQ's by default); unparseable input is kept as typed. WhatsApp links come from `geo.whatsapp_digits`.
- **Controlled lists** (`app/core/lists.py`, Settings → Lists): giving purposes, minister titles/ranks, education levels, story categories, inquiry topics, follow-up types. Forms render only the list; routes accept only `lists.canonical(...)` values (any spelling → the list's own); "Others" keeps the giver's words in `note`. Gender is `lists.gender()` (`male`/`female`).
- `app/core/geo_migration.py` runs at startup (idempotent): fills empty codes from EXACT matches only; anything else is listed on **Admin → Data check**, never guessed. Tests: `tests/test_global.py`.
